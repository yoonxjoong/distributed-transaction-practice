# 2단계. 중복 주문 방지: 멱등 키와 락

## 목표

같은 주문 요청이 여러 번 들어와도(더블 클릭, 클라이언트 재시도) **주문은 한 번만 처리**되도록 만든다.

## 요구사항

- [ ] 주문 요청에 클라이언트가 만든 **요청 ID(멱등 키)** 를 포함한다.
- [ ] 이미 처리된 요청 ID면 새로 처리하지 않고 기존 결과를 반환한다.
- [ ] 동시에 같은 요청 ID가 들어와도 하나만 처리되도록 **락**을 건다.
- [ ] 락 방식 최소 두 가지를 비교한다: DB 비관적 락(`SELECT ... FOR UPDATE`), Redis 분산 락
- [ ] 재고 차감 자체의 동시성도 처리한다 (서로 다른 주문이 같은 상품을 동시에 살 때)

## 완료 기준

- [ ] 같은 요청 ID로 **동시에 100번** 요청해도 주문 1건, 재고·포인트 차감 1번
- [ ] 재고 100개 상품에 서로 다른 주문 100건을 동시에 보내면 재고가 정확히 0
- [ ] 동시성 테스트는 `ExecutorService`와 `CountDownLatch`로 작성한다.

## 직접 재현할 실패 시나리오

1. 락 없이 같은 요청 ID로 동시 요청을 보낸다. 주문이 여러 건 생기는 것을 확인한다.
2. 락 없이 재고 차감을 동시에 실행한다. 갱신 손실(Lost Update)로 재고가 덜 줄어드는 것을 확인한다.
3. 락 획득 후 예외가 나서 락이 해제되지 않으면 어떻게 되는지 확인한다.

## 정리할 질문

- 멱등성이란 무엇이고, 왜 분산 환경에서 필수인가?
- 비관적 락, 낙관적 락, 분산 락의 차이와 선택 기준은?
- 락과 트랜잭션의 범위가 어긋나면 어떤 문제가 생기는가? (트랜잭션 커밋 전에 락을 풀면?)
