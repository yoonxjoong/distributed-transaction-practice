# 6단계. SAGA Orchestration 구현

## 목표

각 서비스가 **로컬 트랜잭션을 바로 커밋**하고, 실패하면 **보상 트랜잭션**으로 되돌리는 방식을 구현한다. 오케스트레이터(주문 서비스)가 전체 흐름을 지휘한다.

## 요구사항

- [ ] 재고·포인트 서비스에 실행 API와 보상 API 추가
  - 재고 차감 ↔ 재고 복구
  - 포인트 차감 ↔ 포인트 복구
- [ ] 오케스트레이터가 단계를 순서대로 실행하고, 실패하면 **완료된 단계를 역순으로 보상**
- [ ] 사가 진행 상태를 DB에 저장 (`saga_instance`: 사가 ID, 현재 단계, 상태)
  - 오케스트레이터가 재시작돼도 이어서 진행하거나 보상할 수 있어야 한다.
- [ ] 모든 실행·보상 API는 멱등
- [ ] 보상 실패 시 재시도, 계속 실패하면 수동 처리 대상으로 표시

## 완료 기준

| # | 상황 | 기대 결과 |
|---|---|---|
| 1 | 모두 성공 | 주문 완료 |
| 2 | 포인트 차감 실패 | 재고 복구, 주문 실패 |
| 3 | 보상(재고 복구) 일시 실패 | 재시도로 결국 복구 |
| 4 | 재고 차감 후 오케스트레이터 재시작 | 저장된 상태로 이어서 진행 또는 보상 |
| 5 | 같은 단계를 중복 호출 | 한 번만 반영 |

## 직접 고민할 것

- 재고는 이미 커밋되어 빠졌는데 주문은 아직 진행 중이다. 이 중간 상태를 다른 사용자가 보면? (격리성 부족)
- 중간 상태를 줄이는 방법: 주문 상태를 `PENDING`으로 두기, 의미적 락(Semantic Lock), 단계 순서 조정
- 보상할 수 없는 작업(예: 이메일 발송)은 사가의 어느 위치에 두어야 하는가?

## 정리할 질문

- TCC와 SAGA Orchestration의 가장 큰 차이는 무엇인가? (예약 후 확정 vs 커밋 후 보상)
- 사가는 ACID 중 무엇을 포기하는가?
- 오케스트레이터 방식의 장점과 단점은? (흐름 파악 쉬움 vs 오케스트레이터 집중)
