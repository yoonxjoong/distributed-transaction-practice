# 7단계. SAGA Choreography 구현

## 목표

중앙 지휘자 없이 **서비스들이 이벤트를 주고받으며** 사가를 진행한다.

## 요구사항

- [ ] `docker-compose.yml`에 Kafka 추가
- [ ] 이벤트 흐름 설계 (예시)
  - `OrderCreated` → 재고 서비스가 차감 → `StockDeducted` 또는 `StockDeductFailed`
  - `StockDeducted` → 포인트 서비스가 차감 → `PointDeducted` 또는 `PointDeductFailed`
  - `PointDeducted` → 주문 서비스가 주문 완료
  - `PointDeductFailed` → 재고 서비스가 복구, 주문 서비스가 주문 실패 처리
- [ ] 이벤트 흐름을 다이어그램으로 먼저 그리고 구현한다.
- [ ] 소비자는 **멱등**하게 처리 (같은 이벤트가 두 번 와도 한 번만 반영)

## 완료 기준

| # | 상황 | 기대 결과 |
|---|---|---|
| 1 | 모두 성공 | 주문 완료 |
| 2 | 포인트 차감 실패 | 재고 복구, 주문 실패 |
| 3 | 같은 이벤트 중복 수신 | 한 번만 반영 |
| 4 | 소비자 서비스가 잠시 내려갔다가 다시 뜸 | 밀린 이벤트를 처리해 결국 정합성 확보 |

## 직접 재현할 실패 시나리오

1. **DB 커밋 후 이벤트 발행 전에 서비스가 죽는다.** 이벤트가 유실되어 사가가 멈추는 것을 확인한다.
2. **이벤트를 먼저 발행하고 DB 커밋이 실패한다.** 없는 일이 이벤트로 퍼지는 것을 확인한다.
3. 위 문제를 해결하는 **Transactional Outbox** 패턴을 조사한다. (구현은 [더 나아가기](../README.md#더-나아가기))

## 정리할 질문

- Orchestration과 Choreography는 각각 언제 적합한가?
- 서비스가 늘어나면 Choreography에서 전체 흐름을 어떻게 파악할 수 있는가?
- "DB 저장과 메시지 발행을 원자적으로 하는 문제"는 왜 생기고 Outbox는 이를 어떻게 해결하는가?
- 최종적 일관성(Eventual Consistency)을 사용자 경험에서 어떻게 보여줄 것인가? (주문 접수됨 → 주문 완료)
