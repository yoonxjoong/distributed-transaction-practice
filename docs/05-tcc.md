# 5단계. TCC (Try-Confirm-Cancel) 구현

## 목표

DB 락 대신 **애플리케이션 수준의 예약**으로 분산 트랜잭션을 구현한다.

## 요구사항

- [ ] 재고·포인트 서비스에 API 3개씩 추가
  - `Try`: 자원을 **예약**한다 (예: 재고를 바로 빼지 않고 예약 수량으로 잡아 둠)
  - `Confirm`: 예약을 확정한다
  - `Cancel`: 예약을 취소하고 자원을 돌려준다
- [ ] 예약 테이블(예: `product_reservation`, `point_reservation`)에 요청 ID, 수량, 상태(`RESERVED`, `CONFIRMED`, `CANCELLED`) 저장
- [ ] 주문 서비스(코디네이터) 흐름
  1. 모든 서비스에 Try
  2. 모두 성공하면 모두 Confirm
  3. 하나라도 실패하면 성공한 Try 전부 Cancel
- [ ] Confirm, Cancel은 **멱등**하게 구현 (여러 번 호출해도 결과 같음)
- [ ] Confirm, Cancel 실패 시 재시도

## 완료 기준

아래 시나리오 테스트가 모두 통과한다.

| # | 상황 | 기대 결과 |
|---|---|---|
| 1 | 모두 성공 | 재고·포인트 차감, 주문 완료 |
| 2 | 재고 Try 성공, 포인트 Try 실패 | 재고 예약 Cancel, 주문 실패 |
| 3 | Confirm 중 한 서비스 일시 장애 | 재시도로 결국 Confirm 완료 |
| 4 | Confirm 또는 Cancel을 두 번 호출 | 두 번째 호출은 아무 변화 없음 |
| 5 | Try 요청이 타임아웃 후 **뒤늦게 도착** (Cancel이 먼저 처리됨) | 늦게 온 Try는 거절되어 예약이 남지 않음 |
| 6 | Try 후 코디네이터가 죽어 Confirm, Cancel이 오지 않음 | 일정 시간 지난 예약은 자동 Cancel |

## 직접 고민할 것

- 예약 상태에서 다른 사용자가 같은 재고를 조회하면 무엇을 보여줘야 하는가? (가용 재고 = 재고 - 예약)
- 시나리오 5처럼 Cancel이 Try보다 먼저 오는 경우를 어떻게 막을까? (빈 Cancel 기록 남기기 등)
- Confirm이 계속 실패하면 최종적으로 어떻게 처리할까?

## 정리할 질문

- TCC의 격리성은 어디서 오는가? 2PC와 무엇이 다른가?
- TCC를 적용하기 어려운 자원은 어떤 것인가? (예약이라는 개념이 없는 외부 API 등)
- 시나리오 5, 6이 왜 TCC에서 특히 중요한가?
