# 1단계. 모놀리식 주문 시스템과 `@Transactional`

## 목표

하나의 애플리케이션, 하나의 DB에서 주문·재고·포인트를 구현하고, **로컬 트랜잭션으로 정합성이 어떻게 보장되는지** 확인한다. 이후 단계의 기준점이 된다.

## 요구사항

- [ ] 상품(`Product`): 상품 ID, 가격, 재고 수량
- [ ] 포인트(`Point`): 사용자 ID, 잔액
- [ ] 주문(`Order`): 주문 ID, 사용자 ID, 주문 항목들, 상태
- [ ] 주문 API: `POST /orders` (사용자 ID, 상품 ID와 수량 목록)
- [ ] 주문 처리 순서: 주문 생성 → 재고 차감 → 포인트 차감 → 주문 완료
- [ ] 재고 부족, 포인트 부족이면 예외 발생

## 완료 기준

- [ ] 정상 주문 시 재고와 포인트가 정확히 차감되고 주문이 `COMPLETED`가 된다.
- [ ] 포인트가 부족하면 **이미 차감한 재고까지 롤백**된다.
- [ ] 위 두 가지를 통합 테스트로 검증한다.

## 직접 재현할 실패 시나리오

1. `@Transactional`을 **빼고** 포인트 부족 주문을 보낸다. 재고만 줄어든 상태가 남는 것을 확인한다.
2. `@Transactional`을 붙인 메서드를 **같은 클래스 안에서 호출**해 본다. 트랜잭션이 적용되지 않는 것을 확인한다. (고급편의 프록시 내부 호출 문제)
3. 체크 예외를 던지면 기본 설정에서 롤백되지 않는 것을 확인한다.

## 정리할 질문

- 로컬 트랜잭션은 ACID 중 무엇을 어떻게 보장하는가?
- `@Transactional`은 내부적으로 어떻게 동작하는가?
- 이 구조에서 서비스를 분리하면 가장 먼저 무엇이 깨질까?
