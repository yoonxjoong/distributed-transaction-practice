# 3단계. MSA로 분리하고 정합성 문제 재현

## 목표

주문·재고·포인트를 **서비스 3개, DB 3개**로 나누고, 로컬 트랜잭션만으로는 정합성을 지킬 수 없다는 것을 **직접 재현**한다. 이 단계에서는 해결하지 않는다.

## 요구사항

- [ ] 멀티 모듈 또는 별도 프로젝트로 `order-service`, `product-service`, `point-service` 분리
- [ ] 서비스마다 자기 DB만 사용 (다른 서비스 DB 직접 접근 금지)
- [ ] 주문 서비스가 HTTP(`RestClient` 등)로 재고·포인트 서비스를 호출
- [ ] `docker-compose.yml`로 DB 3개(필요하면 서비스까지) 한 번에 실행
- [ ] 장애 주입 방법 마련: 특정 요청에서 일부러 예외 발생 또는 지연 (설정값이나 헤더로 켜고 끄기)

## 완료 기준

- [ ] 정상 주문이 서비스 3개를 거쳐 처리된다.
- [ ] 아래 실패 시나리오를 **모두 재현**하고, 각각 어떤 불일치가 남는지 표로 정리한다.

## 직접 재현할 실패 시나리오

| # | 상황 | 남는 불일치 (직접 확인 후 기록) |
|---|---|---|
| 1 | 재고 차감 성공 → 포인트 차감 실패 | |
| 2 | 포인트 서비스가 처리는 했는데 응답 전에 타임아웃 | |
| 3 | 재고 차감 성공 → 주문 서비스가 죽음 | |
| 4 | 주문 서비스가 타임아웃으로 재시도 → 재고 서비스에서 중복 차감 | |

## 정리할 질문

- 주문 서비스의 `@Transactional`은 왜 다른 서비스의 DB 변경을 롤백하지 못하는가?
- 타임아웃은 "실패"인가? 상대 서비스에서 처리됐는지 알 수 없는 상황을 어떻게 다뤄야 하는가?
- 2단계에서 만든 멱등 키를 서비스 간 호출에도 적용해야 하는 이유는?
